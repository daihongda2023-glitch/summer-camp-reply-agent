# 夏令营群聊答疑运营工作台

## Problem Statement

如何让运营老师在微信群中高效处理夏令营学生重复提问，同时保持回复可靠、可审核、可追溯？

## Recommended Direction

建设一个 PC 端客服运营工作台，界面和交互参考微信，但产品定位不是“个人微信自动机器人”，而是面向运营老师的答疑控制台。它承接群聊导入、监听触发、问题识别、回复生成、人工确认、自动回复和知识沉淀。

第一版以半自动模式为主：当监听到 `@Agent`、关键词命中或问号消息时，系统自动使用 FAQ + RAG 生成回复草稿，并填入工作台的回复框。运营老师可以直接发送，也可以编辑后发送。人工修改后的内容不直接覆盖正式知识库，而是进入待审核候选库，由运营确认后再转为 FAQ、RAG 资料或风格样例。

全自动模式后置开放，只允许处理“可以找到明确答案”的低风险问题。必须同时满足：FAQ/RAG 高置信命中、来源明确、问题不涉及个人状态、投诉安全、作业代答、录取面试结果或其他需要人工确认的事项。

## Key Assumptions to Validate

- [ ] 运营老师愿意使用工作台确认草稿，而不是完全依赖自动回复。验证方式：用 20-30 条真实群聊问题做半自动操作演示，观察确认/修改成本。
- [ ] `@Agent`、关键词和问号消息足够覆盖主要学生问题。验证方式：用历史群聊记录统计触发召回率和误触发率。
- [ ] FAQ + RAG 能覆盖第一批全自动场景。验证方式：整理白名单意图，用真实问题集评估命中率和错误率。
- [ ] 人工修改内容进入待审核候选库，比直接覆盖 FAQ 更安全。验证方式：观察候选内容中事实变更、口吻优化和临时通知的比例。
- [ ] 微信风格消息流 + 客服运营侧栏，比纯聊天窗口更适合运营处理。验证方式：做低保真界面后让运营老师走一遍“识别-编辑-发送-沉淀”流程。

## MVP Scope

### 1. PC 端客服运营工作台

- 左侧展示群聊列表、监听状态、未处理问题数。
- 中间展示微信风格消息流，包括学生消息、Agent 草稿、已发送回复和系统状态。
- 右侧展示回复依据、风险标签、候选回复、置信度、审核入口。
- 底部提供回复输入框，半自动模式下自动填入 Agent 草稿。

### 2. 群聊导入

- 选择某个群聊，导入历史消息。
- 导入内容用于高频问题发现、话术风格分析和待审核候选生成。
- 聊天记录不直接作为事实 RAG 来源。

### 3. 监听触发

只处理三类消息：

- 被 `@Agent` 的消息。
- 命中运营配置关键词的消息。
- 含问号且与夏令营相关的消息。

其他闲聊默认忽略，避免过度打扰群聊。

### 4. 半自动回复

- Agent 自动生成回复草稿。
- 草稿自动填入回复框。
- 运营老师可以编辑、发送、转人工、标记待补充。
- 编辑后的内容进入待审核候选库。

### 5. 受控全自动回复

全自动只处理低风险高置信问题，例如：

- 报名入口。
- 报名截止时间。
- 线下时间地点。
- 食宿安排。
- 交通费用。
- 官方通知渠道。
- 已确认的课程或日程说明。

以下问题必须转人工：

- 个人报名状态、录取结果、面试结果。
- 投诉、安全、医疗、突发事件。
- 作业答案、代码代写、评分争议。
- 群聊中临时出现但未被官方资料确认的信息。

### 6. 待审核候选库

人工修改后的回复进入候选库，运营可以选择：

- 加入 FAQ。
- 加入 RAG 正式资料。
- 加入风格样例。
- 忽略。

## Not Doing

- 破解微信数据库。
- 隐藏式模拟用户批量发消息。
- 把微信群聊天原文直接作为事实来源。
- 让人工修改内容直接覆盖正式知识库。
- 对个人状态、录取、面试、投诉、安全、作业答案做自动回复。
- 多账号、多群批量营销能力。
- 第一版不追求完全替代微信客户端。

## Open Questions

- 普通微信阶段，最终发送动作由工作台辅助复制，还是由受控适配器发送？
- 第一批全自动白名单意图具体有哪些？
- 关键词词库是否需要运营界面编辑？
- 监听数据源优先使用 WeFlow 本地 API，还是另做剪贴板/导入兜底？
- 待审核候选库是否需要区分“事实变更”“口吻优化”“临时通知”“新问题”？

## 推荐下一步

1. 输出 PC 端工作台低保真界面方案。
2. 输出监听与回复模式技术方案。
3. 先实现半自动工作台 MVP，再开放受控全自动。
4. 用真实群聊样本验证触发规则和全自动白名单。
