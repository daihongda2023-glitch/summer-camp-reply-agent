# 微信 RAG AI 自动回复设计

## 背景

当前项目已经具备以下能力：

- 微信消息命中触发规则后进入问答链路。
- 优先匹配结构化 FAQ。
- FAQ 未命中时检索本地 RAG 文档。
- 高置信官方 RAG 内容可以进入自动发送流程。
- 社区内容、未知问题、个人状态、作业代写、安全事件等不会自动发送。

现有 RAG 回复直接使用检索到的资料正文，表达形式可能不适合微信群交流。本次改造在不改变 FAQ 优先级和安全边界的前提下，引入真实 OpenAI 模型，将高置信官方 RAG 证据整理为自然、简洁、可直接发送的中文回复。

## 目标

1. 微信消息命中触发规则且 FAQ 不满足自动回复条件时，继续检索 RAG。
2. 只有高置信、`official` 可信等级的 RAG 结果可以调用 AI 生成自动回复。
3. AI 只能依据传入的 RAG 证据回答，不得补充证据中没有的日期、链接、规则或结论。
4. AI 请求失败或输出不合格时，允许降级发送高置信官方 RAG 原文。
5. 社区资料、低置信资料、未知问题和现有人工兜底问题不得因为接入 AI 而升级为自动发送。
6. 使用模拟微信监听器和模拟发送器验证多种 RAG 场景，并使用真实 OpenAI 接口验证生成链路。

## 非目标

- 不让 AI 自主决定是否命中 FAQ 或 RAG。
- 不把结构化 FAQ 统一改为 AI 生成。
- 不让 AI 访问微信历史记录、个人资料或外部网络。
- 不改变现有微信群触发规则、敏感问题兜底规则和社区资料的人工审核要求。
- 不在测试过程中向真实微信群发送消息。

## 方案选择

### 采用：检索后生成

系统继续使用确定性的 FAQ 与 RAG 检索完成事实选择。只有检索器已经确认命中高置信官方资料后，才把用户问题和证据交给模型。模型只承担语言组织职责。

该方案改动范围小，能够保留已有安全策略，也便于在模型不可用时退回官方原文。

### 未采用：FAQ 与 RAG 全部交给 AI

该方案表达风格统一，但会增加 FAQ 回复的延迟、费用和事实漂移风险，不符合本次最小范围目标。

### 未采用：AI 自主调用检索工具

该方案适合更复杂的多步问答，但需要额外的工具权限、循环控制和评估机制。当前场景只需要基于确定证据生成短回复，暂无必要引入自主代理。

## 总体流程

```text
微信消息
  → 触发规则判断
  → 人工兜底规则判断
  → FAQ 检索
      → 高置信且有效：直接使用 FAQ 回复
      → 未满足：RAG 检索
          → 高置信 official：调用 AI 生成
              → 输出合格：使用 AI 回复，标记 rag_ai
              → 请求或校验失败：使用官方 RAG 原文，标记 rag_fallback
          → community：仅生成待审核建议，不自动发送
          → 低置信或无结果：标记待补充，不自动发送
  → 自动模式决策
  → 模拟或真实微信发送适配器
  → 写入处理日志与发送结果
```

## 组件设计

### RAG 回答生成接口

新增独立的回答生成接口，输入包括：

- 原始用户问题。
- RAG 检索结果中的官方证据正文。
- 证据标题、来源地址和可信等级。

输出包括：

- 生成后的回复文本。
- 使用的模型名称。
- 生成状态；至少区分 `generated`、`unavailable`、`invalid`。
- 失败原因，供日志记录使用。

接口使用依赖注入，生产环境接入 OpenAI，单元测试接入可控的假实现，避免测试依赖网络和付费接口。

### OpenAI 实现

使用 OpenAI Responses API。配置约定：

- `OPENAI_API_KEY`：必需的 API 密钥。
- `OPENAI_CHAT_MODEL`：可选，默认 `gpt-5.6-luna`。
- `OPENAI_BASE_URL`：可选，默认 `https://api.openai.com/v1`。
- 请求超时默认 15 秒，避免长时间阻塞微信轮询。

选择 `gpt-5.6-luna` 是因为当前任务属于高频、短文本、证据约束明确的生成工作，需要优先考虑响应速度和成本。模型配置保留环境变量覆盖能力，避免将业务逻辑绑定到单一模型。

请求使用结构化输出，至少返回：

```json
{
  "answer": "面向学生的中文回复",
  "grounded": true
}
```

系统提示明确规定：

- 只能使用提供的证据。
- 不知道时不得猜测。
- 不得新增证据中不存在的 URL、日期、数字、规则或承诺。
- 回复面向微信群学生，直接回答问题，不展示内部分析过程。
- 默认保持简洁，不输出 Markdown 标题或代码块。

OpenAI 官方资料：

- Responses API 文本生成：<https://developers.openai.com/api/docs/guides/text>
- 结构化输出：<https://developers.openai.com/api/docs/guides/structured-outputs>
- 模型选择：<https://developers.openai.com/api/docs/guides/latest-model>

### 输出校验

即使模型返回 `grounded: true`，仍执行本地确定性校验：

- `answer` 必须是非空字符串。
- 去除首尾空白后长度不得超过 600 个字符。
- 不得包含模型拒答、内部提示词或 JSON 外壳。
- 回复中出现的 HTTP/HTTPS 链接必须能够在输入证据或证据来源中找到。
- 返回结构不符合约定时视为无效输出。

校验失败不修改 RAG 事实，只触发官方原文降级。

### 问答引擎集成

`AnswerEngine` 保持现有优先级：人工兜底、FAQ、RAG、未知问题。

当 RAG 结果满足以下全部条件时调用生成器：

- `trust_level == "official"`。
- `is_strong == true`。
- 检索结果包含非空证据。

生成成功时返回：

- `action = "auto_reply"`
- `intent = "rag.document"`
- 回复文本为 AI 输出。
- 来源继续使用 RAG 原始来源，不能把 OpenAI 标记为事实来源。
- 增加回复生成方式 `rag_ai` 供日志和界面展示。

生成失败时保留同样的事实来源，回复文本使用现有 RAG 原文，并把生成方式标记为 `rag_fallback`。

FAQ 回复标记为 `faq`；社区建议维持 `suggested_reply`，不能进入自动发送。

### 默认运行时

默认工作台会同时加载本地 RAG 检索器和 OpenAI 回答生成器。缺少 API Key 或初始化失败时，回答生成器处于不可用状态，但不阻断程序启动；高置信官方 RAG 继续通过原文降级策略工作。

### 日志与展示

在不记录 API Key、完整提示词或额外个人信息的前提下，记录：

- 回复生成方式：`faq`、`rag_ai`、`rag_fallback`、`rag_community`、`needs_info`。
- OpenAI 模型名称。
- AI 失败类型：缺少配置、超时、HTTP 错误、响应解析错误或输出校验失败。
- 原始 RAG 来源地址与可信等级。
- 最终是否进入自动发送以及模拟发送验证结果。

## 错误处理

| 情况 | 处理方式 |
| --- | --- |
| 缺少 `OPENAI_API_KEY` | 不调用接口，官方高置信 RAG 降级为原文自动回复 |
| 请求超时、网络错误或服务端错误 | 记录失败类型，降级为官方 RAG 原文 |
| API 返回拒答或结构异常 | 视为无效输出，降级为官方 RAG 原文 |
| AI 新增无依据链接 | 本地校验拦截，降级为官方 RAG 原文 |
| RAG 为 `community` | 仅保留人工审核建议，不调用 AI 自动回复 |
| RAG 低置信或未命中 | 不调用 AI，不自动发送 |
| 命中个人状态、作业代写或安全兜底 | 按现有规则转人工，不检索 RAG，不调用 AI |

## 测试策略

所有生产代码修改遵循测试驱动开发：先添加失败测试并确认失败原因，再实现最小代码使其通过。

### 单元测试

- OpenAI 请求包含模型、系统约束、问题和 RAG 证据。
- 正确解析 Responses API 的结构化输出。
- 缺少密钥、请求超时、HTTP 错误和异常响应能返回可降级状态。
- 空回复、超长回复和无依据链接会被本地校验拒绝。
- FAQ 命中不会调用生成器。
- 官方高置信 RAG 会调用生成器并返回 `rag_ai`。
- AI 失败会返回官方原文并标记 `rag_fallback`。
- 社区、低置信和未知内容不会进入 AI 自动回复。

### 模拟微信闭环

通过模拟监听器产生微信消息，通过真实问答引擎处理，通过模拟发送适配器记录最终发送内容，至少验证：

1. “请问能否公开下载比赛镜像？”：FAQ 未命中，RAG 命中，AI 生成并自动发送。
2. “页面选了 3.7.2.1，服务器里为什么还是 3.7.1.5？”：自然改写问题能够命中版本差异资料并自动发送。
3. “MACA C++、Triton 和 TileLang 是放在一个榜里比吗？”：命中不同语言评测资料并自动发送。
4. “报名入口在哪里？”：FAQ 命中，确认不调用 AI。
5. “CMake 构建失败怎么办？”：只命中社区经验，确认不自动发送。
6. “营服是什么颜色？”：无资料，确认不调用 AI、不自动发送。
7. 模拟 AI 超时：确认使用官方 RAG 原文完成自动发送。
8. 模拟 AI 返回无依据链接：确认校验拦截并使用官方原文。

### 真实 OpenAI 联调

使用本机已有 `OPENAI_API_KEY`，对前三个 RAG 场景发起真实 Responses API 请求。验证：

- 模型能够返回合格的结构化输出。
- 回复内容能回答原问题且不超出证据。
- 回复中的链接均来自证据。
- 最终内容经过完整工作台链路到达模拟发送器。

真实联调只发送模拟问题和公开 RAG 资料，不包含微信群聊天记录或个人信息，也不会连接真实微信发送器。

## 验收标准

1. FAQ 未命中且官方 RAG 高置信命中时，AI 生成内容能够进入微信自动发送链路。
2. AI 不可用或输出不合格时，高置信官方 RAG 原文能够自动发送。
3. FAQ、社区资料、未知问题和人工兜底的既有安全行为没有回归。
4. 至少三个不同主题的 RAG 场景完成“消息输入—检索—AI 生成—模式决策—模拟发送—日志记录”闭环。
5. 至少一次真实 OpenAI 接口联调成功；若外部服务临时不可用，自动化测试仍能完整验证协议、降级和微信闭环。
6. Python 全量测试和桌面端现有测试全部通过。

## 安全与隐私

- 只向 OpenAI 发送当前模拟或真实触发消息，以及已公开的 RAG 证据。
- 不发送历史群聊、联系人信息、API Key 或本地配置内容。
- 不在日志中记录 API Key、Authorization 请求头或完整内部提示词。
- 事实来源始终指向原始 RAG 文档，模型不是事实来源。
- 自动发送权限仍由现有触发规则、可信等级、置信度和自动模式共同控制。
