# 桌面端体验简化设计

## 背景

当前桌面端已经具备微信观察、FAQ/RAG 检索、AI 生成、自动发送和消息持久化能力，但操作入口较多、内部术语暴露明显，默认窗口尺寸也无法完整承载三栏工作台。用户需要在不理解 `send_mode`、`debug_review_mode` 等实现细节的前提下，快速判断系统是否可用、当前消息为什么需要处理，以及下一步应该做什么。

## 设计目标

1. 用“安全试运行、人工辅助、自动回复”三个业务模式代替分散的技术开关。
2. 首屏直接展示运行检查，明确微信窗口、AI 服务、目标群和监听状态。
3. 每条消息只突出一个推荐操作，其余动作收进“更多操作”。
4. 待处理与历史记录均支持搜索，状态、来源、置信度和时间可快速扫描。
5. 发送、审核、转人工等异步动作具备忙碌态、成功提示和自动选中下一条。
6. 默认窗口完整展示工作台；托盘驻留并仅对待审核、发送失败和服务错误发通知。
7. 普通用户只看到基础设置，高级参数折叠展示，未完成的高级页面不再暴露。
8. 回复依据先展示业务结论，技术分数放入折叠详情；来源链接可安全打开。
9. 提供键盘快捷键，修改后的回复在确认发送时沿用现有候选沉淀能力。

## 交互模型

### 运行模式

| 模式 | 底层配置 | 用户体验 |
| --- | --- | --- |
| 安全试运行 | `manual_confirm` + 调试审核开启 | 所有消息进入待审核，便于调规则 |
| 人工辅助 | `manual_confirm` + 调试审核关闭 | 命中后生成草稿，由人工确认发送 |
| 自动回复 | `auto_send` + 调试审核关闭 | FAQ 或 RAG 任一命中即发送；均未命中则待审核 |

### 推荐操作

- 安全试运行：主操作为“确认回复并填入微信”。
- 人工辅助：主操作为“填入微信”；填入后主操作切换为“我已发送”。
- 自动回复：进入队列的消息通常需要人工判断，主操作为“转人工处理”。
- 历史记录：只读展示，不提供会改变消息状态的操作。

### 信息层级

工作台采用三栏布局：左侧为运行状态和模式，中间为队列与回复编辑，右侧为回复依据。默认窗口增大并设置最小尺寸；窄屏时按主内容、状态、依据的顺序自然降级。

回复依据先显示“建议动作、命中来源、置信度等级、简短原因”，综合/语义/FAQ/RAG 原始分数放入折叠区域。界面不再出现“旧规则”“内部模式”等开发术语。

## 状态与通知

- 所有操作在执行期间禁用相关按钮并显示明确动词。
- 操作成功后刷新队列、选中下一条，并展示短时反馈。
- 应用关闭主窗口时驻留托盘；托盘可重新打开工作台或设置页。
- 仅新增待审核消息、自动发送失败或服务异常触发系统通知，正常自动发送不打扰用户。

## 安全与兼容

- 三种业务模式仅映射现有后端配置，不改变原有发送判定语义。
- 外部来源仅允许 `http:` 和 `https:`，由主进程调用系统浏览器打开。
- 保留现有 IPC 与后端接口，新增接口采用向后兼容字段。
- 高级页面代码暂时保留以兼容旧链接，但从普通设置入口隐藏。

## 验收标准

1. 新用户打开应用即可看到运行检查和下一步建议。
2. 用户只需选择一个运行模式，不需要组合多个开关。
3. 每条待处理消息只有一个明显主操作，执行中不会重复提交。
4. 处理成功后消息从待处理队列消失并自动选中下一条。
5. 队列和历史记录可以按关键词搜索，历史仍可按状态筛选。
6. 来源 URL 可点击且只允许安全协议。
7. 默认窗口能完整展示三栏，关闭后应用驻留托盘。
8. Python 测试、桌面静态检查、TypeScript 类型检查和生产构建全部通过。
